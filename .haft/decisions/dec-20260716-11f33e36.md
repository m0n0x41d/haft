# V1 algebraic typed-memory core with bounded COV-2, manually activated ProjectTypeEnvExtension, registered canonical codecs, and a V5 legacy migration shell

## 1. Problem Frame

**Signal:** Haft currently stores coarse artifact kinds and free-string edges. Reliance-bearing project records do not expose the FPF C.2.1 episteme positions, context-local kind claims, or typed relation signatures, so the MCP boundary cannot prevent category errors or let a later agent recover the project's ontic neighborhood around the current entity of concern.

**Constraints:**
- The current FPF revision and its author publications remain semantic authority; Haft must not recreate a shadow ontology or silently reinterpret changed rules.
- EntityOfConcern is modeled as EntityOfConcernSlot/entityOfConcernRef filled by a U.Entity, never as a new U-kind or universal node kind.
- Context-local U.Kind, intent, extent, scope, SubkindOf, dependency, parthood, and slot filling remain distinct.
- N-ary slot relations, cardinality, ValueKind, RefKind, governing pattern, bounded context, and source provenance must be representable without flattening them into ambiguous binary strings.
- Open-world not-recovered or underdetermined state remains distinct from invalid and from asserted absence.
- Type validation may reject structurally or ontologically inadmissible assertions, but it must not present type conformance as truth, evidence, authorization, or completed work.
- The graph never derives causal, temporal, or project-work order from insertion order, rank, generic edge direction, card order, or walkthrough order.
- Ordinary local reversible reasoning remains conversational; only reliance-bearing results are persisted.
- Haft remains local-first, single-binary, SQLite-backed, and usable without a mandatory external graph server.
- Binding decisions and commissions remain human-authorized and fail closed.
- Existing artifacts and Markdown projections remain readable and migrate without silent semantic invention or data loss.

**Acceptance:** A pure typed core represents project entities, context-scoped kind claims, epistemes, claims, n-ary relation instances, slot assignments, carriers, and source provenance. A versioned source-derived schema projection supports exact symbol/definition/reference traversal and generic slot validation. MCP returns Valid, Invalid, or Underdetermined diagnostics with rule anchors and repairs. Reliance-bearing artifacts require or explicitly defer an entity-of-concern settlement; existing artifacts are migrated or marked unresolved without invention. Status and graph queries pivot on EntityOfConcern facets and preserve local next-use/stop/return without a global NextAction. E2E tests cover the four seminar category errors, a valid episteme-to-code/spec/evidence neighborhood, FPF update failure safety, and lossless legacy readability.

## 2. Decision

**Selected:** V1 algebraic typed-memory core with bounded COV-2, manually activated ProjectTypeEnvExtension, registered canonical codecs, and a V5 legacy migration shell

**Selection policy:** First eliminate any canonical architecture that fails FPF-model soundness or the local-first single-binary operating boundary. Among survivors, maximize the lower of typed-agent service power and schema-evolution safety; use migration burden only as a tie-break. Accept the V1 plus V5 split only if V1 remains the sole semantic core, compiler coverage is bounded COV-2 with honest source-only gaps, generic MemoryChangeSet cannot mint schema, the project-local extension lifecycle is manually activated, ByValue uses the admitted registered-codec contract, and the GoldenConcernBundle, artifact adapters, and identity-reconciliation conditions are mandatory acceptance gates.

**Why selected:** V1 is the only compared canonical architecture that satisfies both the FPF-model-soundness and local-first single-binary floors while preserving open-world Underdetermined results, source provenance, and replaceable storage. V5 is retained only for additive tables, dual-read, single-write-new, unresolved legacy posture, and reversible migration. Gap A keeps project-local schema out of generic memory writes: Haft-local signatures compile from a versioned Local-Practice/DPF carrier and become usable only through a sealed manual ProjectTypeEnvExtension activation. Gap B makes ByValue deterministic and tamper-evident through registered pure codecs whose mechanism is separate from TypeEnv admission, a closed ValueShape algebra, private VerifiedTypedValue construction, and mandatory ClaimGraphCodecV1. The selection is load-bearing only together with task-oriented artifact adapters, explicit entity reconciliation, reliance-gated unsettled persistence, and one real GoldenConcernBundle proving that the graph helps an agent recover a project concern rather than merely type-check empty records.

**Transformation record:**
- Kind: target-state transformation only; not method, work authorization, evidence, or publication.
- Transformed entity: HaftSoftwareSystem typed project-memory semantic boundary
- Initial state: Legacy artifacts and free-string or binary links are useful carriers and read sources, but there is no single FPF-typed canonical n-ary relation-slot write model, project-active TypeEnv admission basis, artifact-adapter contract, or entity reconciliation boundary.
- Post state: One pure V1 algebraic core and AdmissionService govern canonical semantic writes; bounded COV-2 compiles supported explicit FPF declarations; versioned Local-Practice/DPF carriers compile into manually activated project extension DAGs; exact TypeEnv bindings admit registered pure canonical codecs and private VerifiedTypedValue values including ClaimGraphCodecV1; V5 supplies additive legacy migration mechanics only; versioned artifact adapters and explicit identity reconciliation populate and recover a real GoldenConcernBundle.
- Relation: replaces migrated reliance-bearing semantic writes while preserving legacy reads and unresolved provenance
- Context: Haft v9 typed EntityOfConcern-centered project memory


**Invariants:**
- FPF source is the sole authority for FPF meaning; slides, examples, lexical matches, and graph proximity emit no type rules.
- V1 is the sole canonical semantic core and V5 is only a migration, storage, and legacy-read shell.
- The first compiler scope is bounded COV-2: structurally supported A.6.5, C.2.1, and C.3.1 declarations and individually complete supported constraints may compile; heterogeneous A.14, A.15, and A.22.CGUS prose stays source_only or unsupported until source-owned normalized declarations exist.
- EntityOfConcern is a governed relation slot filling by a U.Entity, not a universal stored kind or permanent entity label.
- N-ary relations retain named slots and arbitrary source-target-type edges are never canonical semantic writes.
- Missing source, bridge, admission, identity, or compiler basis yields Underdetermined or unsettled, never fabricated Valid, Invalid, or identity.
- One canonical EntityID survives admitted aliases and explicit append-only merge or split history; retrieval rank never merges identities.
- IdentityChange is the closed instance-level AdmitAlias, MergeEntities, SplitEntity, or SupersedeAlias union and never mutates TypeEnv schema.
- Generic MemoryChangeSet cannot declare or admit local kinds, relation signatures, ValueShapes, or codec bindings; those exist only in a disjoint source-compiled TypeEnvExtensionProposal and become usable only after sealed manual activation.
- The project-active TypeEnv is one exact FPF base plus a canonically resolved acyclic ProjectTypeEnvExtension DAG with exact imports, provides, provenance, compatibility diff, revalidation, and project binding.
- CodecRegistry supplies pure executable mechanism only; the active TypeEnv separately admits the exact ValueKindRef to ValueShapeRef plus CodecRef binding.
- ValueShape is a closed scalar, record, sum, ordered-sequence, unordered-set, or dedicated-ClaimGraph algebra with no arbitrary JSON variant.
- Only the pure verifier can construct VerifiedTypedValue, whose domain-separated length-prefixed digest commits to exact ValueKindRef, ValueShapeRef, CodecRef, and canonical bytes.
- Every supported C.2.1 episteme signature has exactly one mandatory ByValue ClaimGraphSlot using ClaimGraphCodecV1.
- Missing active signature, codec, or type rule is Underdetermined; known malformed bytes, digest mismatch, or explicit SlotSpec mismatch is Invalid; unavailable historical codecs yield inspect-only OpaqueStoredValue.
- Canonicalization semantics never change under an existing CodecRef; changed rules require a new ref, compatibility diff, and explicit value or assertion migration.
- Task-oriented adapters shield ordinary callers from raw slot assembly but use the sole AdmissionService and do not define parallel validation semantics.
- Ordinary bounded conversation persists nothing; explicit or reliance-bearing unresolved carriers may remain unsettled without an EntityOfConcern assertion.
- Type conformance is not truth, Evidence, authority, causal force, completed Work, or FPF-pattern applicability.
- Binding decisions, commissions, specification lifecycle changes, project-profile changes, and TypeEnv activation remain on their sealed manual or gated interfaces.
- Assertions are append-only; correction uses explicit retract or supersede events and historical TypeEnv snapshots remain inspectable.
- Graph, Markdown, code index, recall, RDF, and UI are projections rather than canonical semantic write models.
- Graph direction, rank, timestamps, mantras, and walkthrough order never create a global work sequence or NextAction.
- Legacy artifacts remain readable and byte-preserved throughout migration and rollback.

## 3. Rationale

**Counterargument:** A much smaller evolution of the existing artifact graph could deliver useful recall sooner; V1 may impose a large compiler, extension-authoring, codec, identity, migration, and adapter burden while returning Underdetermined for much of FPF, leaving Haft with a beautifully typed but sparsely populated store. Manual extension activation may also make first use substantially heavier than a normal local memory tool.

**Selected variant weakest link:** FPF does not yet publish one normalized declaration grammar for the desired semantic surface, and Haft must now own both a rigorous local-practice extension lifecycle and canonical codec suite. The architecture will create little product value if extension activation, task adapters, codecs, or entity reconciliation are too ceremonial for agents to populate a useful graph.

**Rejected alternatives:**

|---------|---------|--------|
| V1 algebraic typed-memory core with bounded COV-2, manually activated ProjectTypeEnvExtension, registered canonical codecs, and a V5 legacy migration shell | **Selected** | V1 is the only compared canonical architecture that satis... |
| V1 without gated local schema, canonical codecs, mandatory adapters, reconciliation, and GoldenConcernBundle | Rejected | It proves an abstract relation algebra but allows generic writes or Go tables to become schema, leaves ByValue underspecified, and does not prove useful agent memory; callers could still face raw slot ceremony and identity duplication while the canonical graph remains empty. |
| V2 canonical RDF, OWL, SHACL, and PROV knowledge graph | Rejected | It still requires Haft-specific source compilation, tri-state admission, authority, and migration semantics while adding reification and embedded-runtime complexity. Keep it as a possible export. |
| V3 canonical TypeDB typed relation database | Rejected | A mandatory external runtime violates the current local-first single-binary boundary and does not remove Haft's compiler, authority, or legacy migration work. |
| V4 canonical Datalog fact and rule engine | Rejected | Datalog does not itself supply durable identity, carriers, authority, event history, or migration semantics, and unsafe completeness assumptions could collapse Underdetermined into false. A limited monotone Rule IR may remain internal to V1. |

## 4. Consequences

**Rollback plan:**
Triggers:
- a pinned FPF revision cannot rebuild covered TypeEnv rules without a hidden handwritten catalog or silent rule loss
- the acceptance corpus produces material false Invalid results where Underdetermined is required
- cross-process TypeEnv or graph-revision tests permit a stale or duplicate semantic write
- legacy import loses carrier bytes, guesses entity identity or relation meaning, or creates duplicate identity
- task adapters remain dependent on caller-authored raw slot arrays or disagree silently with kernel validation
- the GoldenConcernBundle requires hand-seeded SQL or cannot be recovered exactly after rebuild
- alias collision, merge, or split erases or silently conflates identity or relation provenance
- generic MemoryChangeSet can declare or admit a kind or relation signature, or an adapter auto-declares a missing signature
- ProjectTypeEnvExtension activation occurs without exact base and candidate refs and digests, compatibility and existing-assertion revalidation, expected graph revision, project binding, and human receipt
- codec registration is treated as ValueKind admission, arbitrary JSON reaches canonical ByValue, or a caller constructs VerifiedTypedValue
- ClaimGraph canonicalization loses node or edge identity, accepts duplicate or dangling content, or changes meaningful order
- canonicalization changes under an existing CodecRef or historical unavailable codec bytes are silently reinterpreted
- generic admit crosses a manual authority boundary
Steps:
1. disable new typed admission and base or extension activation while retaining exact read and inspect access to committed typed history
2. preserve the SQLite database, semantic events, base and extension snapshots, activation records, canonical value bytes and CodecRefs, projection debt, and an exact export
3. keep legacy carriers and legacy reads available without re-enabling migrated free-edge writers
4. disable or revert typed transports and task adapters while retaining typed_historical, legacy_unbound, and unresolved read posture
5. reopen the architecture with failed prediction evidence and compare a reduced V1 slice or newly justified alternative
6. never back-translate typed n-ary relations into lossy binary or free-string edges
Blast radius: typed-memory core, FPF and local-extension compiler, codec registry and canonical values, additive SQLite schema, artifact adapters, entity reconciliation, CLI and MCP contracts, graph and recall projections, skills, migration tooling, and affected typed-memory specifications; legacy carriers and read history remain available

**Refresh triggers:**
- FPF publication revision, source-adapter grammar, or compiler coverage changes for an enforced rule
- A.6.0, A.6.5, C.2.1, C.3.1, A.14, A.15, A.22.CGUS, or E.4.DPF source semantics change
- Haft Local-Practice/DPF carrier edition, extension imports or provides DAG, local signature, ValueShape, CodecSpec, or canonicalization version changes
- a real project produces a false Invalid, missing canonical Change or Relation form, or unresolved adapter mismatch
- a new binding artifact kind or authority class is introduced
- legacy migration requires a semantic guess or a writable bypass is discovered
- entity alias, context, merge, split, or project-profile identity assumptions change
- the GoldenConcernBundle or any prediction misses its threshold
