## 3. Rationale

**Counterargument:** The checked-out FPF README and ToC already give a capable coding agent a workable search path. A custom source index and Query surface add parser, schema, and maintenance cost and still cannot prove that the agent applied the right pattern. Until a held-out comparison exists, raw source plus rg and a strong agent remains the required null baseline, and Query must not claim retrieval superiority.

**Selected variant weakest link:** The hard cut spans the source adapter, derived index, CLI and MCP contracts, generated host carriers, skill behavior, navigation/status semantics, and retired legacy files. A stale shared-file hunk, generated carrier, or active SpecSection could leave the public story internally inconsistent even while focused Query tests pass.

- Mechanical controls are admitted as substantive FPF concerns, exact inspect broadens into search, or role-local ambiguity is hidden behind one winner.
- Legacy project artifacts become unreadable or DecisionRecord and WorkCommission binding ceases to fail closed without verified human authority.
- The source-native changes cannot be separated from later profile, migration, and typed-memory work well enough to produce a reproducible byte manifest.
Steps:
1. Stop all v9 readiness, release, and superiority claims while retaining the failing source, query, and carrier evidence.
2. Restore the last coherent pre-v9 public surface from version control without rewriting historical project artifacts.
3. Rebuild the derived FPF index from the pinned publication and verify that historical carriers remain readable.
4. Reopen this implementation decision with the failed target-level evidence; do not patch a new hidden route into Query.
Blast radius: FPF source parsing and derived index, CLI and MCP Query surfaces, managed host instructions and skills, status/navigation semantics, and public migration documentation; existing project-memory artifacts remain historical data and are not rewritten by rollback.
