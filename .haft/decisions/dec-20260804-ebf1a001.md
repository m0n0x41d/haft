# Automatically activate every proven-compatible ProjectTypeEnv successor without operator interaction

## 1. Problem Frame

**Problem statement:** Haft currently stages a later ProjectTypeEnv successor but requires an operator-mediated head-selection request even when the exact successor is proven compatible with the current project. This leaks an internal schema lifecycle into product UX, blocks automatic uptake of compatible FPF and Local-Practice rules, and makes dogfood and user projects drift unnecessarily.

## 2. Decision

**Selected:** Automatically activate every proven-compatible ProjectTypeEnv successor without operator interaction

**Selection policy:** For every mutation-capable project reconciliation path, automatically activate the exact latest staged successor if and only if its closed predecessor, project binding, Base and extension DAG, Stage identity, compatibility classification, existing typed assertion revalidation, and current project-profile posture are all current and admissible at CAS time. Never ask the operator in that case. If compatibility is false, incomplete, stale, or underdetermined, write no new head and return an exact diagnostic.

**Why selected:** The operator directly set one project-wide v9 policy: every project must switch to new rules automatically whenever compatibility is proven, and nobody should be asked. Automatic activation removes the false human gate while retaining exact compatibility proof, revalidation, atomic CAS, append-only history, and fail-closed behavior outside the compatible case.

**Transformation record:**
- Kind: target-state transformation only; not method, work authorization, evidence, or publication.
- Transformed entity: Haft ProjectTypeEnv successor activation policy
- Initial state: Every later non-default successor is staged and requires an exact host-routed operator selection before ProjectTypeEnvHead can advance.
- Post state: Every exact proven-compatible successor advances ProjectTypeEnvHead automatically without a prompt; only incompatible or underdetermined cases stop with no write and an exact diagnostic.
- Relation: supersedes the manual-activation part of dec-20260716-11f33e36 and narrows the TypeEnv operator-mediated branch of dec-20260801-a60e3d56
- Context: Haft v9 source-native FPF and typed-memory release contract
- Window: v9


**Invariants:**
- A proven-compatible ProjectTypeEnv successor is activated automatically and never requires an operator question.
- Dogfood and user projects use the same compatibility and activation policy.
- Compatibility proof is exact, source-current, project-bound, profile-aware, assertion-revalidated, and rechecked at atomic CAS time.
- Incompatible, incomplete, stale, or underdetermined transitions perform no head write and return an exact diagnostic.
- Historical TypeEnv bases, extension DAGs, stages, activations, values, and provenance remain immutable and readable.
- Every current activation delta and typed-memory graph event records the exact authority generation: `compatible_successor_policy` for automatic compatible activation and `host_routed_operator_request` for explicit host-routed selection. Legacy `manual_type_env_activation` carriers remain decode-and-replay history only.
- Generic MemoryChangeSet cannot declare schema or authorize a TypeEnv transition.
- Automatic compatible activation grants no DecisionRecord, SpecSection, WorkCommission, release, or other authority.

## 3. Rationale

**Counterargument:** A manual gate makes every schema-semantic change visible to a human and can protect against a faulty compatibility classifier. But it asks users to approve internal mechanics they cannot meaningfully evaluate and creates fleet drift; the safer boundary is a strict machine-checkable compatibility proof with atomic no-write failure, not ritual confirmation.

**Selected variant weakest link:** The system must define proven-compatible narrowly and trigger reconciliation on every supported project upgrade/open path without turning read-only commands into hidden writers; missing a mutation-capable entry point can leave a project temporarily stale until its next reconciliation.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Automatically activate every proven-compatible ProjectTypeEnv successor without operator interaction | **Selected** | The operator directly set one project-wide v9 policy: eve... |
| Require operator selection for every non-Genesis ProjectTypeEnv successor | Rejected | Rejected because a proven-compatible transition changes no project-owned semantic choice and the prompt exposes internal lifecycle machinery, creates drift, and blocks automatic FPF rule uptake. |
| Activate every newer successor regardless of compatibility | Rejected | Rejected because incompatible or underdetermined changes can invalidate existing assertions or profile applicability and must remain fail-closed. |
| Auto-activate only in dogfood | Rejected | Rejected because compatibility semantics and user experience must be identical for Haft itself and every user project. |

**Evidence requirements:**
- Focused transition tests prove automatic compatible activation, idempotence, no prompt or operator-request dependency, exact CAS, and no-write negative cases.
- Schema-57 migration tests preserve legacy activation rows byte-for-byte while proving that new activation deltas, authority-use rows, and graph events agree on the exact current authority generation.
- Fresh-init, v8.1 upgrade, and isolated dogfood probes converge through product lifecycle paths.
- Full ordinary Go suite, static gates, race qualification, P13, P14 contract qualification, and manual E2E are rerun on one exact candidate after implementation.

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| Every proven-compatible ProjectTypeEnv successor is activated automatically without an operator request. | Transition and lifecycle integration tests across dogfood, fresh-init, and upgrade fixtures. | One idempotent head advance and zero prompts/operator-request dependencies in every compatible case. |
| All other successor classifications remain fail-closed. | Negative transition matrix for incompatible, incomplete, stale, and underdetermined cases. | Zero head writes and exact diagnostics. |

## 4. Consequences

**Rollback plan:**
Triggers:
- A transition classified compatible causes an existing typed assertion or admitted project profile to become invalid.
- An incompatible, stale, or underdetermined successor changes ProjectTypeEnvHead.
- Automatic reconciliation loses append-only activation history or violates expected-revision CAS.
- A supported mutation-capable upgrade path leaves a compatible project on the predecessor without an exact diagnostic.
Steps:
1. Disable automatic successor activation at the reconciliation coordinator while preserving all historical heads, stages, receipts, values, and source snapshots.
2. Restore the last proven-valid predecessor head through a separately implemented atomic recovery effect only for affected projects.
3. Correct the compatibility or trigger defect and rerun migration, transition, race, and installed-runtime qualification before re-enabling automatic activation.
Blast radius: ProjectTypeEnv successor reconciliation, init and upgrade paths, project-local SQLite head state, public onboarding and TypeEnv UX; immutable historical bases and values remain preserved.

**Refresh triggers:**
- Compatibility taxonomy, compiler coverage, assertion revalidation, project-profile applicability, Stage identity, or head CAS semantics change.
- A supported init, upgrade, open, migration, or reconciliation entry point changes.
- A compatible project remains stale or any non-compatible project advances.
- FPF or Local-Practice source changes alter compiled TypeEnv semantics.
